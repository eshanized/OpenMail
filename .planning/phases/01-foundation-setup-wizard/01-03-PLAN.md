  <action>
    Build the complete IMAP authentication flow with throttling, session management, and security.

    **Step 1: Register IMAP auth guard in AppServiceProvider.** Per research Pattern 3: use `Auth::viaRequest('imap', ...)` in boot(). The guard: (1) gets email + password from request, (2) finds or creates User by email (firstOrCreate), (3) connects to IMAP server using stored config from openmail.php (imap_host, imap_port, imap_encryption), (4) authenticates with user's credentials, (5) on success returns $user, on failure returns null. Per pitfall 6: NEVER log the password. Use `Log::channel('security')` with redacted fields only.

    **Step 2: Configure auth.php.** Add 'imap' guard: `['driver' => 'session', 'provider' => 'users']`. The Closure Request Guard handles the actual IMAP validation. Add 'users' provider: `['driver' => 'eloquent', 'model' => App\Models\User::class]`.

    **Step 3: Build LoginForm Livewire component.** Per D-16: email + password fields. Wire:model (deferred) on both — NOT wire:model.live. Login method:
    1. Validate input: email required|email, password required
    2. Check throttle: per D-14, use RateLimiter::for('login') with dual-key (IP + email). If too many attempts, throw ValidationException with seconds remaining message.
    3. Attempt IMAP auth: `Auth::guard('imap')->attempt(['email' => $this->email, 'password' => $this->password])`
    4. On success: session rotation (per AUTH-04: `$request->session()->regenerate()`), clear throttle hits, redirect to /mailbox
    5. On failure: increment throttle hit, show "Invalid email or password" (never reveal which field failed — per security best practice)
    6. Store encrypted IMAP password in session for future IMAP connections: `session()->put('openmail:imap_password', Crypt::encrypt($this->password))` — per research recommendation and PROJECT.md constraint "never store mailbox passwords in plaintext"

    **Step 4: Configure rate limiter.** Per D-14 and research Pattern 4: in AppServiceProvider boot(), register `RateLimiter::for('login', ...)`. Dual-key: per-IP (10 attempts per minute) + per-email (5 attempts per 5 minutes). Use database cache driver (per ADR-003: no Redis). The throttling thresholds from D-14 are enforced in the LoginForm component, not the RateLimiter itself (RateLimiter provides atomic counting; LoginForm applies the progressive delays).

    **Step 5: Implement progressive throttling in LoginForm.** Per D-14:
    - 1st-2nd fail: no delay
    - 3rd fail: 5s delay (show message "Try again in 5 seconds")
    - 5th fail: 30s delay
    - 7th fail: 5min delay
    - 10th fail: 15min lock
    Track attempts in cache with key `login_attempts:{email}`. On success, clear the counter. On failure, increment and calculate next delay.

    **Step 6: Configure session security.** Per D-13: SESSION_LIFETIME=1440 (24h). Per D-15: http_only=true, same_site=lax, secure=env('SESSION_SECURE_COOKIE'). Per AUTH-06: secure cookies. Ensure config/session.php has all these values. SESSION_DRIVER=database (per DB-02).

    **Step 7: Update login Blade view.** Per D-06: user-friendly error messages. Show "Invalid email or password" for auth failures. Show "Too many attempts. Try again in X seconds" for throttling. No technical details on login page (security). Use Tailwind for styling. CSRF token via @csrf.

    **Step 8: TLS enforcement (AUTH-08).** Per D-12: default ports 993/465 with SSL/TLS. In config/openmail.php, defaults must be SSL encryption. ImapConnectionTester already uses these defaults. Add validation: if user changes encryption to None, show warning "Unencrypted connections are not recommended for production."

    **Step 9: Test the full flow.** Create Pest test: login with valid IMAP credentials → session created, user authenticated. Login with invalid credentials → error shown, no session created. Login 3 times with wrong password → 5s delay. Verify session rotation on successful login. Verify CSRF token present. Verify cookie flags.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → LoginForm | Email + password submitted via Livewire. CSRF protected. |
| LoginForm → IMAP Server | Credentials validated against external mail server. Must use TLS. |
| Session Store | Database-stored sessions. Encrypted cookies prevent tampering. |
| Logout → Session | Session invalidation must be complete (invalidate + regenerate token). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | Credential stuffing | high | mitigate | Dual-key rate limiter (IP + email); progressive delays per D-14 |
| T-03-02 | Information Disclosure | IMAP password exposure | high | mitigate | Crypt::encrypt() before session storage; never logged; never in DB |
| T-03-03 | Tampering | Session fixation | high | mitigate | Session rotation on login (AUTH-04); $request->session()->regenerate() |
| T-03-04 | Tampering | CSRF on login | medium | mitigate | @csrf directive; VerifyCsrfToken middleware (AUTH-05) |
| T-03-05 | Information Disclosure | Password in transit | medium | mitigate | TLS enforcement (AUTH-08); port 993/465 with SSL default |
| T-03-06 | Tampering | Session reuse after logout | medium | mitigate | Session invalidation + token regeneration on logout (AUTH-07) |
| T-03-07 | Information Disclosure | User enumeration | medium | mitigate | Generic "Invalid email or password" message; never reveal which field failed |
| T-03-08 | Denial of Service | Brute force lockout | low | mitigate | Progressive delays prevent lockout DOS; 15min lock after 10th attempt |
</threat_model>
